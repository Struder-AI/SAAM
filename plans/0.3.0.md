# SAAM 0.3.0 intent

Owner intent, 2026-09-30, corrected 2026-10-01. **Maps express causal flow; significant further map 0 refactors require owner discussion.** Completed SAAMpath motion planning belongs to 3; 7 wraps specialized workspaces; 9 owns reusable machine/material settings. This release consolidates architecture, engines, extensions and desktop deployment. Former features move to [0.4.0](0.4.0.md), including material overlap. Physical qualification continues across releases.

## Owner decisions

- Assign every declaration to map 0; files may contain several buckets. Keep small general utilities private per bucket; shared domain rules need explicit interfaces. Refine submaps after root boundaries settle, preserving current capabilities.
- Every wire denotes a specific inspectable/printable interface or small set. Arrows show causal information/actions; each contract separately lists permitted call/read directions, which may be opposite. No other interaction or transitive permission is granted. The original sketch's Geometry → Toolpath/Bundle and Toolpath → Bundle were causal flows, not reversed calls.
- Consolidate geometry into an engine; integrate all toolpath construction through Inject, Trace and Slice. Migrate existing skills into the extension format, distinguishing engine primitives from extension compositions rather than reproducing legacy implementations behind wrappers.
- The active bundle is the only **non-exclusive/shared part-state object**, not the only object with state. Studio owns its private state exclusively; so may engines, jobs and installation services. No component reaches into another's mutable state. Shared part changes cross the bundle interface. Agent ↔ Bundle retains active-bundle switching and state reads; content changes use Geometry, Toolpath and Settings. Bundle stores exact selected settings snapshots.
- Support desktop Codex and desktop Claude Code only; no web agents or separate offline-operation design. SAAM works without an activation code. An invite entered in Studio connects official alpha testers to updates and diagnostics; unactivated use gets neither service. Keep the former relay as an update service/diagnostics monitor, not a chat relay.
- Testers install during chat by giving their desktop agent a URL. Extensions live separately from bundles and contain guidance, scripts using the geometry/toolpath engines, or both. Bundles declare extension dependencies required to regenerate/render them in Studio.
- Builder escalation permits extension creation/modification, including locally changing release-bundled extensions. Good tester extensions should be straightforward to share or integrate into subsequent releases.
- Maker guidance and context assembly belong to 1, including extension manuals; 4 supplies extension discovery and 9 supplies printer capabilities for manual filtering. Remove Studio’s unused direct extension request hooks; interactive additions use 7. Extensions may access external resources through an explicit wire/interface: Thingi10K is an extension, not a geometry-engine responsibility. Resource access includes declared search/retrieval; the Internet is transport, not an implicit permission for every component.
- Aim for stable engines and preserve local extensions/bundles across updates. Do not build a speculative compatibility framework, support-window policy or migration system now; issue migration guidance if engine changes require it.
- Extensions are ordinary local code, without promised technical sandboxing or enforced IO permissions. Review contributions individually before adopting them. Map boundaries describe intended/conformance-checked SAAM and adopted-extension interactions, not security confinement of arbitrary user scripts.
- Keep the Connect-panel explanation simple. No diagnostics collection from unactivated users; connecting with an invite explains updates and alpha diagnostic collection. Feature preservation still needs an explicit investigation.

## Feature review decisions
- Remove web-chat operation and its connection/session machinery; preserve a simpler Studio–agent request/event channel.
- Preserve priority event delivery: alert-level events notify the agent live and carry queued lower-priority observations. Existing `studio/studio-events.mjs` already implements delivered/held classes. Its current tool-result/explicit-read drains can also deliver held events without an alert; that detail is noted for review, not silently changed. This agent queue is separate from live diagnostic emission to the service.
- Keep and rethink the tour. Move some introductory explanation into an additional outside reference (PDF or webpage; format undecided), retaining useful interactive teaching in Studio.
- An agent may own several Studio instances; separate agents own separate instances. **Only one instance may edit a given bundle at a time.** Other viewing instances do not gain edit ownership; ownership/release behavior needs implementation through the bundle interface.
- Saved bundle geometry remains viewable without its extension dependencies. A saved toolpath likewise remains viewable when present, even if missing extensions prevent regeneration.
- Apply text, heat-set inserts and Thingi10K become extensions, preserving their useful operations. Migration of their current core implementation does not mean dropping the capabilities.
- Items 8–9 (techniques and geometry preservation) belong to the geometry task. Item 10: keep current machine/exporter scope. Item 11: no viewing-feature removal is proposed; ordinary Studio behavior stays, subject to the separate tour rethink. Item 12: 9 owns remembered setup behind an explicit interface.
- Item 13: Studio may prepare component 8’s checked output once before review; Export confirms and delivers those exact bytes without another check or ceremony. Hide Export immediately when an update is queued, using the waiting indicators’ same pending-update state. Changed content and revision checks remain; unchanged interpretation is reused. Item 14 has no additional decision beyond the existing release deferral.

## Specialized workspaces (accepted direction)

Component **7 Specialized workspaces** wraps private design UI/state. Public engines 2/3 supply geometry and candidate SAAMpaths; 5 creates reproducible bundles. Reusable construction belongs in Extensions. The wing example launches with `npm run workspace:wing`: full-plane display, wing-only printing, integrated upturned winglets, straight rod passages and upright continuous Trace curves. Outer sections print on the flat winglet face. No flight qualification is claimed. Only the standalone renderer was adopted from TK-DEV `217a6e0`; the new construction uses current APIs.

The handoff is **one-way creation followed by ordinary Studio work**. Save all bundles creates one set folder under `Prints/wing-workspace` (or `SAAM_DATA`), with `design.json`, an `export.json` inventory and one self-contained bundle per piece. Each carries geometry, explicit Trace construction, source parameters and protected construction requirements; thermal settings and placement remain editable. A single copied agent request addresses the whole set. SAAM owns generation, machine export/checking and user confirmation. Regeneration creates a new set, preserving Studio edits; requirement-breaking edits require explicit source detachment. No live synchronization, shared generation coordinator or wholesale prototype/PR adoption is implied.

## Inventory and boundary comparison

The architecture audit now inventories runtime declarations/module bodies, applies exact provisional ownership, and compares observed accesses against explicit contract access endpoints and entry bindings. New/orphan assignments, unknown effects and non-analyzed files stay visible. Unlike default maps it includes toolkit/exporters/extensions. It uses lexical/import resolution and literal couplings; whole-runtime receiver/holder propagation proved too expensive and remains an analysis gap. This is a negotiation report, not certified conformance.

| Requirement | Necessary change / acceptance |
|---|---|
| Automatic complete inventory | Scan the release/runtime surface, including toolkit, exporters, extension host, module initialization and installation/service edges. State what is analyzed, external/vendor/native, unsupported or excluded; never silently drop a leaf. One implementation leaf has one owner; new/unassigned/ambiguous/orphan leaves stay visible. Semantic ownership is reviewed, not guessed from directory names. |
| Bind implementation | Implemented initial exact declaration/module assignments in ownership.json, separate from generated inventory/evidence. Files may mix owners; declarations may not. New/orphan leaves remain visible; command hosts and extension computations have distinct ownership. |
| Compare intended/observed | Audit separates missing root connections, direction review, represented pairs, entry bindings, unknown effects and unassigned code with source previews. Entry binding verifies a target/kind only; typed arguments, effects, timing and functional equivalence remain unchecked. |
| Inspect complete interfaces | Wires retain exact contracts, operations, inputs/outputs, effects, errors and exclusions. Observed calls carry manual source evidence; boxes preview files/sections/declarations. Typed schemas, complete caller/effect coverage and ownership/conformance bindings remain work. |
| No hidden pathways | Follow/restrict imports/re-exports, aliases, callbacks/closures, mutable records, registries, dynamic loading, filesystem paths, HTTP, workers, process/environment/global state and native/WASM calls. Shared schemas/assets are dependencies too. Unknown dynamic endpoints block verification; runtime observations cannot prove absence. |
| Enforce boundaries | Check actual API entry points and imports/effects in SAAM and reviewed/adopted extensions. Flag bypasses rather than claiming a runtime sandbox. Arbitrary local extensions may access the host and are unverified unless analyzed; their unknown interactions cannot receive a conformance guarantee. |
| Honest verification | Distinguish design validity, inventory completeness, boundary compliance and behavior. Stale scans, incomplete scope or unresolved relevant effects cannot pass compliance. Show findings on the overview/affected wire; never hide them to improve complexity scores. |

## Extension and deployment proposals

- Use a stable installation-instructions URL resolving a version-pinned packaged release, with digest verification and OS/client requirements. A repository checkout is a separate developer workflow. Exact URL and OS matrix remain open.
- Working name: **Release & diagnostics service**. Activation gates only updates/alpha diagnostics, never making, viewing or exporting a part. A missing/invalid code or service failure does not disable SAAM. No offline grace/revocation subsystem is requested.
- Keep extension/dependency identity, entry points and assets simple and explicit; preserve local edits separately from replaceable release defaults. Exact packaging/dependency representation is still a submap decision, not a mandate for multiple version registries or automated migration machinery.
- Thingi10K and other resource-using extensions document their IO and return assets with identity and available provenance/license metadata. The caller saves imported assets in the bundle; scripts remain separate. Prefer saved assets over repeat downloads. Resource access is a conventional interface, not a permission broker or sandbox; contributions are reviewed case by case.
- Exchange portable extension packages with manifest, guidance/scripts, assets and provenance/license. Import does not execute scripts. Promotion is reviewed and explicit; no automatic collection of tester scripts/bundles.
- Keep user storage outside the replaceable installation and retain clear errors when required extensions are missing. Handle breaking changes with specific migration guidance when needed.

### Diagnostic proposal

SAAM has a **live diagnostic emitter**: tool calls and other runtime events chirp directly to the connected service. Emit useful [D-039](../DECISIONS.md#d-039--alpha-relay-records) fields—operation parameters/results, errors, durations, Studio events and environment/connection information—at local SAAM boundaries for both desktop clients. This is not preservation/migration of old records or a local record-then-upload pipeline; no offline backlog/backfill. The service may retain received events as it does today. Additional proposed events/fields:
- Correlate commands, bundle revisions and generation/export jobs across agent, Studio and workers; include stage start/end, elapsed time, last progress, cancellation, worker exit and error stack. Preserve failure location even when the worker cannot finish a result.
- Add extension identity and local-modification marker, exporter/machine profile, input-size counts and available native-helper versions to existing SAAM/OS/Node metadata. Record install/update phase and outcome so a failed launch is distinguishable from an inactive tester.
- Enable emission only for activated testers; no diagnostics collection or retrospective upload of pre-activation activity. Keep existing compaction, redact credentials and sensitive URL/path fields, and exclude chat transcripts/reasoning and bulk files. Retain the existing 30-day service retention provisionally rather than inventing a policy framework.
Suggested Connect statement: “SAAM works without a code. Connecting with an alpha invite enables updates and sends live SAAM diagnostic events—including operation parameters/results, errors, timings and system information—to help us diagnose problems. Large geometry/file payloads are omitted; chat transcripts and credentials are not collected. Received events are kept for 30 days.” Final wording follows the actual implemented payload.
