# SAAM 0.3.0 intent

Owner intent, 2026-09-30. **Map 0 accepted by the owner; submaps are provisional and acceptable for now.** This release reduces complexity through enforced component boundaries, completes engine integration, and establishes desktop extensions and deployment. Former feature intentions move to [0.4.0](0.4.0.md). This supersedes their previous scheduling, including material overlap. Physical qualification continues across releases.

## Owner decisions

- Work top-down: the owner authors map 0 and likely several levels beneath it; agents fit implementation and lower nesting to those boundaries. Scan all leaves automatically; reduce leaf complexity last. Target the simplest useful architecture independent of today's files, preserving most current capabilities.
- Every wire denotes a specific interface or explicit small set of interfaces, completely inspectable in the viewer and printable by an agent. No other interaction path is allowed. Opposite directions may be distinct interfaces. A connection grants no transitive permission.
- Consolidate geometry into an engine; integrate all toolpath construction through Inject, Trace and Slice. Migrate existing skills into the extension format, distinguishing engine primitives from extension compositions rather than reproducing legacy implementations behind wrappers.
- The active bundle is the only **non-exclusive/shared part-state object**, not the only object with state. Studio owns its private state exclusively; so may engines, jobs and installation services. No component reaches into another's mutable state. Shared part changes cross the bundle interface.
- Support desktop Codex and desktop Claude Code only; no web agents or separate offline-operation design. SAAM works without an activation code. An invite entered in Studio connects official alpha testers to updates and diagnostics; unactivated use gets neither service. Keep the former relay as an update service/diagnostics monitor, not a chat relay.
- Testers install during chat by giving their desktop agent a URL. Extensions live separately from bundles and contain guidance, scripts using the geometry/toolpath engines, or both. Bundles declare extension dependencies required to regenerate/render them in Studio.
- Builder escalation permits extension creation/modification, including locally changing release-bundled extensions. Good tester extensions should be straightforward to share or integrate into subsequent releases.
- Extensions may access external resources through an explicit wire/interface: Thingi10K is an extension, not a geometry-engine responsibility. Resource access includes declared search/retrieval; the Internet is transport, not an implicit permission for every component.
- Aim for stable engines and preserve local extensions/bundles across updates. Do not build a speculative compatibility framework, support-window policy or migration system now; issue migration guidance if engine changes require it.
- Extensions are ordinary local code, without promised technical sandboxing or enforced IO permissions. Review contributions individually before adopting them. Map boundaries describe intended/conformance-checked SAAM and adopted-extension interactions, not security confinement of arbitrary user scripts.
- Keep the Connect-panel explanation simple. No diagnostics collection from unactivated users; connecting with an invite explains updates and alpha diagnostic collection. Feature preservation still needs an explicit investigation.

## Feature review decisions

- Remove web-chat operation and its connection/session machinery; preserve a simpler Studio–agent request/event channel.
- Preserve priority event delivery: alert-level events notify the agent live and carry queued lower-priority observations. Existing `studio/studio-events.mjs` already implements delivered/held classes. Its current tool-result/explicit-read drains can also deliver held events without an alert; that detail is noted for review, not silently changed. This agent queue is separate from live diagnostic emission to the service.
- Keep and rethink the tour. Move some introductory explanation into an additional outside reference (PDF or webpage; format undecided), retaining useful interactive teaching in Studio.
- An agent may own several Studio instances; separate agents own separate instances. **Only one instance may edit a given bundle at a time.** Other viewing instances do not gain edit ownership; ownership/release behavior needs implementation through the bundle interface.
- Saved bundle geometry remains viewable without its extension dependencies. A saved toolpath likewise remains viewable when present, even if missing extensions prevent regeneration.
- Apply text, heat-set inserts and Thingi10K become extensions, preserving their useful operations. Migration of their current core implementation does not mean dropping the capabilities.
- Items 8–9 (techniques and geometry preservation) belong to the geometry task. Item 10: keep current machine/exporter scope. Item 11: no viewing-feature removal is proposed; ordinary Studio behavior stays, subject to the separate tour rethink. Item 12: preserve remembered setup behind an explicit private owner/interface.
- Item 13 remains under discussion: the owner wants confirmation inherent in the user's export action, without continual approval/byte-check ceremony. Preserve that design goal; whether and how exact-output identity is implemented must be justified as an internal invariant, not an additional user task. No runtime check has been removed. Item 14 has no additional decision beyond the existing release deferral.

## Specialized workspaces (accepted direction)

The owner accepted the evaluation task's workspace model: a specialized application produces a print bundle as an **external client**, adding no core coordinator or shared-state owner. It may use the public geometry and toolpath engines during design, including candidate paths to evaluate a strategy and revise geometry. Reusable specialized construction logic belongs in Extensions; application-specific UI and temporary design state belong to the workspace.

“Export bundle” transfers named geometry/regions, a reproducible construction recipe, process intent (orientation, path angles/types, bead dimensions), explicit requirements versus editable defaults, and regeneration parameters/assets/extension dependencies. It does not merely transfer a mesh or an unexplained transient browser path. SAAM owns subsequent generation, machine export/checking and exact-output user confirmation; requirement-breaking edits must be visible and unsupported requirements explicit.

For 0.3.0 the handoff is **one-way creation followed by ordinary Studio work**; live synchronization and simultaneous workspace/Studio editing are out of scope. Precise interfaces still need definition. Accepted concept does not authorize merging [PR #23](https://github.com/Struder-AI/SAAM/pull/23) or adopting the separate wing prototype wholesale. The evaluation task inspected policy head `99404d7` and TK-DEV prototype `217a6e0`, without running its demo; its report describes concept/display geometry, not a complete printable-wing implementation. This parent task has not inspected the proposal itself.

## Accepted top map; provisional submaps and contracts

The same viewer supports [030-architecture](../dev-map/sets/030-architecture/architecture.json) and separate [030-deployment](../dev-map/sets/030-deployment/architecture.json). Commands are in the [map guide](../dev-map/README.md#authoring). The sketch is the owner's `20260930_211155.jpg`; its question marks are unresolved design, not instructions from a third party.

| Index | Proposed boundary |
|---|---|
| 1 Maker context | Numbered guidance, with roles/entry and capability manuals. Indexes identify architectural concepts, not just code. |
| 2 Geometry engine | 2.1 Slice-only geometry; 2.2 public construction/import/transform/query API; 2.3 private shared numerical/representation kernel. Deeper capability grouping is provisional. |
| 3 Toolpath engine | 3.1 Inject, 3.2 Trace, 3.3 Slice; 3.4 composition/finalization owns their common output. “Toolpath engine” is the proposed name. |
| 4 Extensions | Library/resolution, execution, and declared external-resource access. Agents may run extensions to acquire assets or construct values. No direct bundle, Studio, private geometry or export access. |
| 5 Active bundle | Revisioned edit/dependency state, generation/artifact state and review/delivery state. Sole shared authority for a part. |
| 6 Studio | UI/private state, bundle presentation and agent channel. Commands into 5 and snapshots/events out of 5 are distinct contracts; requests and prioritized observations reach the owning agent through an explicit channel. |
| 7 Build & export | Evaluate recipe, generate SAAMpath, export/check through machine adapters. Receives a pinned snapshot and returns artifacts; no general coordinator or event bus. |

The agent can use both public engines and extension guidance, then commit declarative edits through 5. Generation runs from 5 through 7; engines return values to their caller instead of writing the bundle. The geometry/toolpath connection is specifically **3.3 → 2.1**: Slice calls its dedicated geometry query API. This reverses the sketch's arrow because arrows follow calls, including their stated response; geometry values return along that contract. Public geometry and Slice-only geometry do not grant access to each other. Sharing through 2.3 is explicit.

The overview lifts nested connections but retains precise endpoints/contracts: its 3 → 2 wire opens 3.3 → 2.1. The owner can revise grouping and permitted callers to reduce wiring on both sides together. No solver may move owner-authored boundaries.

## Scanner and map-system changes required

Today's scanner derives code leaves, call/data/state links and some file/HTTP/worker/event/dispatch links. Manual sets still select exact scanned leaves, empty clusters dissolve, and indexes follow layout. Default scope leaves toolkit/exporters outside and excludes non-JavaScript/native implementations. Unresolved findings mean absent wires do not establish absent interactions. Grouping alone cannot enforce this intent.

| Requirement | Necessary change / acceptance |
|---|---|
| Author before code | Design sets accept empty components, guidance and external actors plus contracts, without fictitious code leaves. Stable component/contract IDs; numbering/positions are presentation. Preserve authored nesting through scans. **Initial design/read/view support implemented here.** |
| Automatic complete inventory | Scan the release/runtime surface, including toolkit, exporters, extension host, module initialization and installation/service edges. State what is analyzed, external/vendor/native, unsupported or excluded; never silently drop a leaf. One implementation leaf has one owner; new/unassigned/ambiguous/orphan leaves stay visible. Semantic ownership is reviewed, not guessed from directory names. |
| Bind implementation | Keep generated inventory/evidence separate from authored ownership/contracts. Collect leaves, assign them under fixed boundaries, then regenerate. Do not auto-place forbidden edges out of sight or fold helpers across ownership boundaries. A legacy leaf spanning components needs splitting. |
| Compare intended/observed | Conformance mode distinguishes permitted/evidenced, proposed/unimplemented, forbidden and unknown. Check endpoint, operation and medium against a contract, not just component-pair connectivity. Report bypasses, undeclared operations and missing owners with source evidence. |
| Inspect complete interfaces | Each wire enumerates operations, input/output schemas, errors, effects, state ownership, callers, callbacks/events, version and source bindings. Aggregate wires retain each contract separately. Initial viewer contracts are semantic proposals; typed schemas/source bindings remain work. |
| No hidden pathways | Follow/restrict imports/re-exports, aliases, callbacks/closures, mutable records, registries, dynamic loading, filesystem paths, HTTP, workers, process/environment/global state and native/WASM calls. Shared schemas/assets are dependencies too. Unknown dynamic endpoints block verification; runtime observations cannot prove absence. |
| Enforce boundaries | Check actual API entry points and imports/effects in SAAM and reviewed/adopted extensions. Flag bypasses rather than claiming a runtime sandbox. Arbitrary local extensions may access the host and are unverified unless analyzed; their unknown interactions cannot receive a conformance guarantee. |
| Honest verification | Distinguish design validity, inventory completeness, boundary compliance and behavior. Stale scans, incomplete scope or unresolved relevant effects cannot pass compliance. Show findings on the overview/affected wire; never hide them to improve complexity scores. |

This deliverable adds authored design sets and clickable/printable proposed interfaces to the existing viewer. **Inventory attachment, source bindings and conformance enforcement are planned, not implemented or certified.** Existing generated implementation maps remain separate. Authored map validation cannot prove runtime encapsulation.

## Extension and deployment proposals

- Use a stable installation-instructions URL resolving a version-pinned packaged release, with digest verification and OS/client requirements. A repository checkout is a separate developer workflow. Exact URL and OS matrix remain open.
- Working name: **Release & diagnostics service**. Activation gates only updates/alpha diagnostics, never making, viewing or exporting a part. A missing/invalid code or service failure does not disable SAAM. No offline grace/revocation subsystem is requested.
- Keep extension/dependency identity, entry points and assets simple and explicit; preserve local edits separately from replaceable release defaults. Exact packaging/dependency representation is still a submap decision, not a mandate for multiple version registries or automated migration machinery.
- Thingi10K and other resource-using extensions document their IO and return assets with identity and available provenance/license metadata. The caller saves imported assets in the bundle; scripts remain separate. Prefer saved assets over repeat downloads. Resource access is a conventional interface, not a permission broker or sandbox; contributions are reviewed case by case.
- Exchange portable extension packages with manifest, guidance/scripts, assets and provenance/license. Import does not execute scripts. Promotion is reviewed and explicit; no automatic collection of tester scripts/bundles.
- Keep user storage outside the replaceable installation and retain clear errors when required extensions are missing. Handle breaking changes with specific migration guidance when needed.

### Diagnostic proposal

SAAM has a **live diagnostic emitter**: tool calls and other runtime events chirp directly to the connected service. Emit useful [D-039](../DECISIONS.md#d-039--alpha-relay-records) fields—operation parameters/results, errors, durations, Studio events and environment/connection information—at local SAAM boundaries for both desktop clients. This is not preservation/migration of old records or a local record-then-upload pipeline; no offline backlog/backfill. The service may retain received events as it does today. Additional proposed events/fields:
- Correlate commands, bundle revisions and generation/export jobs across agent, Studio and workers; include stage start/end, elapsed time, last progress, cancellation, worker exit and error stack. Preserve failure location even when the worker cannot finish a result.
- Add extension identity and local-modification marker, exporter/machine profile, input-size counts and available native-helper versions to existing SAAM/OS/Node metadata. Record install/update phase and outcome so a failed launch is distinguishable from an inactive tester.
- Enable emission only for activated testers; no diagnostics collection or retrospective upload of pre-activation activity. Keep existing compaction, redact credentials and sensitive URL/path fields, and exclude chat transcripts/reasoning and bulk files. Retain the existing 30-day service retention provisionally rather than inventing a policy framework.
Suggested Connect statement: “SAAM works without a code. Connecting with an alpha invite enables updates and sends live SAAM diagnostic events—including operation parameters/results, errors, timings and system information—to help us diagnose problems. Large geometry/file payloads are omitted; chat transcripts and credentials are not collected. Received events are kept for 30 days.” Final wording follows the actual implemented payload.

## Work order and open decisions

1. Preserve accepted map 0. Refine submaps and exact API responsibilities as work descends. Current operation names are proposals, not commitments to many shallow functions.
2. Add inventory/ownership/conformance support. Gather all leaves, surface unknowns and classify every cross-boundary interaction before claiming a sealed boundary.
3. Impose top boundaries, consolidate geometry, finish toolpath integration and migrate skills/extensions. Descend through child boundaries; optimize leaves last. Remove superseded paths as consumers migrate.
4. Implement simple separate user storage, optional activation/update/diagnostics and extension exchange; check preservation of real bundles and modified local extensions. Add migration guidance only for actual breaking changes.
5. Check representative retained workflows through actual Studio/export. Maintain a capability matrix naming retained, deliberately removed and deferred behavior: “most features” must not hide regressions.

Additional obligations: geometry units/tolerances/identity; schema/asset ownership; deterministic resolution; concurrent agent/Studio edits; cancellation/stale completion; crash-safe commits; machine profile/exporter ownership; native dependency compatibility/rollback. One user confirmation binds exact settings, geometry/dependencies and checked program; relevant changes invalidate it, and delivery cannot regenerate behind it. Consolidation implies no new scheduling, collision, support or geometry features.

Open for review: remaining feature preservation/removals; submap/API granularity, workspace handoff and asset packaging; useful diagnostic additions; service name and install endpoint/OS matrix. Map 0's seven core components remain accepted, with workspaces as external clients. Geometry consolidation has its own user-facing task. Workspace concept acceptance does not adopt a particular implementation.
