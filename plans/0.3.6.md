# SAAM 0.3.6 intent

Owner, 2026-10-05: mesh import repair and blob field ship in 0.3.6, after the 0.3.4/0.3.5 Update verification releases.

| Item | Evidence, direction and acceptance | Status |
|---|---|---|
| Mesh repair redesign | Windows 0.3.2 brain imports and a moon import fail CGAL self-intersection repair; likely brain sources reproduce the rejection, while the exact tester inputs remain unidentified. Relaxing genus preservation also fails. Consider general solid-boundary reconstruction using exact triangle-intersection arrangements and oriented winding classification, with libigl/CGAL as a candidate. Further consideration must settle semantics, backend and feasibility before implementation approval. Any selected approach must preserve intended cavities and unaffected geometry, report changes, retain original bytes/cancellation and pass closed-manifold/contact checks, exact decimal STL reimport and prior successful imports. [Investigation](../DEVLOG.md#2026-10-02--record-mesh-import-investigation-and-owner-decisions) owns evidence and coverage limits. | In 0.3.6: `cgal-solid-repair/3` (Windows helper; Mac without native repair). Replacing CGAL with SAAM's own repair: [0.3.7](0.3.7.md) |
| Use SAAM, else an extension | Owner, 2026-10-05, after a tester's agent built a vase-mode program in a custom script (formula-driven shape; a bug killed a print; too-fine tolerance; an over-conservative RAM check): "If saam can do it, use saam. If it can't, build an extension that can." Most things should be doable with extensions; building outside extensions is a SAAM bug the agent reports. Maker and builder guidance state this route; a `saam` command files the bug report to the relay (as Studio's Report a bug). | Implemented: `MAKERS.md#working-boundaries`, `saam call report_bug` |
| Approved 0.3.4/0.3.5 rows | Owner, 2026-10-05: every approved, unimplemented row from [0.3.4](0.3.4.md) and [0.3.5](0.3.5.md) ships in 0.3.6 (tray open without a fixed timeout, dimming by client turn-end signal, couplings C1 and C2, approved dev-map follow-ups). Owner-pending rows stay there. | Tray, dimming, C1 and C2 implemented; profile-limit decisions in progress; dev-map follow-ups open |
| Dimensions and tolerances | Owner, 2026-10-05, on mesh contact pairs failing a 1e-9 mm rule: "I don't know why the hell we are doing anything at 1e-9 mm"; crucial intent for 0.3.6. Everything in SAAM, and anyone building extensions, works from the dimensions SAAM actually deals with (build volumes of hundreds of mm, nozzles and lines of tenths of a mm, layers of hundredths, machine and program resolution near 1e-3 mm) and uses tolerances derived from them, each naming what it protects. Audit and replace arbitrary tolerances; guidance for developers and builders keeps tolerance awareness in the culture and checks keep it from drifting. Mesh repair follows: features far below print resolution produced by repair are closed and reported, not rejected. | In 0.3.6: classes, guidance, ratchet, mesh repair `/3`. Migration of the remaining literals, rounding guards derived from functional tolerances and the vertex merge move to [0.3.7](0.3.7.md) |
| Advanced vase tiles keep their size | Owner, 2026-10-05: an advanced vase mode where the tile does not stretch with the vase's diameter: a wider part of the vase (higher up, say) has more courses per layer than a narrower part. Today pattern X is in perimeter turns, so a fixed course count per turn stretches with the perimeter. | Implemented: sized patterns `{paths, tileWidthMm, riseMm, turns}`; example `flared-sized-loops` |
| Dimming means the agent is at the SAAM desk | Owner, 2026-10-05, refining 0.3.5's turn-end row: dimmed means the agent is working at the SAAM desk, not interacting with the person; un-dimmed means it is at the counter, messaging in chat (or has been, and nothing changed since). Two moves from desk to counter: the agent finishes something, or the person interjects in chat mid-turn; later SAAM work moves it back. Both on Claude Code and Codex where the client allows; Design approved (owner, 2026-10-05; .local/team/dimming-design.md with its six recommendations): result-changing SAAM work dims; client events (Claude Code Stop, StopFailure, UserPromptSubmit, idle_prompt, SessionEnd in settings.json; Codex Stop, Interrupt, UserPromptSubmit, SessionEnd in ~/.codex/hooks.json, trusted once by the person; `notify` untouched) un-dim through the chat hand-back; subagent events ignored. | Implemented; real-client owner checks pending |
| Machine adapters for builders | Owner, 2026-10-05: a friendly way for builder agents to build export adapters for new machines, as extensions have: guidance, sensible standards (the owner reviews the standards list before adoption) and, most importantly, a standard set of plugs a new machine adapter plugs into. Today each machine has an exporter and a player that decodes its program for Studio (`core/export/*.mjs`, `*-player.mjs`). Owner decision, 2026-10-05: the viewer shows the SAAMpath, not a decoded program. Adapters are responsible for translating SAAMpath accurately into their machine format; a new adapter's verification checks are debug-only and are removed once it is known to work. SAAMpath and machine settings are the only transfer medium into an adapter: any other link from Toolpath or Geometry to an adapter must be shown to the owner with its case and specifically approved, otherwise it is not allowed (existing links included). | Implemented: machine extensions under machines/<id>/, `createAdapter(Export)` plug, Studio draws the path, machines/README.md "Adding a machine". Not yet reviewed by the owner: standards S1–S10 (S4 re-adds checks the owner rejected) and the viewer drawing the prepared path rather than the saved SAAMpath |
| Retire fingerprint ceremony | Owner, 2026-10-05: the print fingerprint "isn't actually doing anything, it's just meaningless ceremony". Canonical hashes of the recipe (which carries the whole mesh inline) are recomputed many times per load and edit (the save pause) and re-verify SAAM's own output; no relay record shows any of their checks ever firing. Bundle is the only writer of part state, so an edit itself clears approval and marks the program stale; content hashes remain only where bytes arrive from outside SAAM, taken once. Owner decision, 2026-10-05: "no fingerprint, no approvals. We have bundle state and single operator." Stored approvals and print fingerprints are removed; the person's export in Studio confirms the current state. | Implemented |
| Tray instances on the first menu; Studio tab title | Owner, 2026-10-06: the tray takes three submenus to reach the instances; put them all on the first menu, no submenus whatsoever. The browser tab reads "Installed 0.3.5 - …", truncated; it should read "SAAM Studio 0.3.5 …" followed by whatever instance identifier is needed. | Implemented; owner checks on the installed build |
| Older default phase colours | Owner, 2026-10-06: "We have feedback that the older default colors were better." Restore the pre-0.3.3 toolpath colours (before edfc997b replaced TOOLPATH_COLORS/skinPhase) as the default palette; print choice and local preference stay. | Implemented |
| Intent tree | Owner, 2026-10-06: "I want an intent tree. The versioned intent docs essentially define the spec unless something overrides it." Also: "Did we not also institute forward intent reading? That's a part of the tree everyone should know about too." [intent/](../intent/README.md). | Implemented (e4fac946, dbfd0410) |
| Visual check for agents | Owner, 2026-10-06: "Visual check should be IN (we used to always give the agent an image after geometry or toolpath generation finished - why don't we do that anymore, and we should, please attend to it)." | Implemented (W5): `visualCheck` image paths on geometry and generation results; agent-determined views and storage await owner review |
| Slice overlap check | Owner, 2026-10-06: "It doesn't matter if areas overlap by a small amount in 3D printing. That should never kill a print or a toolpath generation. It does matter if large areas try to print into each other". "what we need is a slice-stack to slice-stack boolean." "And we can check trace curves against slice surfaces too." "Report rather than refuse is good." "X should be .1mm." Region sharing stays in [0.4.0](0.4.0.md). | Moved to [0.3.7](0.3.7.md) (in progress) |
| Adaptive memory limits | Owner, 2026-10-06: "memory limits must be adaptive and appropriately sized for the system." | Moved to [0.3.7](0.3.7.md) (in progress) |
| Read-only commands start nothing | Owner, 2026-10-06, on two Studio windows with no chat: "Did these fail? What exactly were they intended for, and why didn't they work?" Found: `saam help` from a checkout started its runtime inside the installed SAAM. | Implemented (aa32cd5a); stale tray icons removed by the trays themselves; on-screen check pending |
| Testing source checkout changes | Owner, 2026-10-06: "testing of source checkout changes, which will not touch the orchestrator itself, is also done on the same saam orchestrator. If source checkout changes DO affect the orchestrator, they can't be tested until after the update" (the owner's required statement, "or equivalent"). Also: "I don't want separate SAAM orchestrators." "Let's not change orchestrator itself". Visible sessions for people and background sessions for agents (listed in the tray) both run the checkout's runtime under the home's one installed orchestrator and report to the relay. | Applies once 0.3.6 is installed; background sessions in runtime code: [0.3.7](0.3.7.md) |
