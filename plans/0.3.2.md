## Installed release and two startup directions

Owner requirement, 2026-10-01: **support both Studio → desktop chat and desktop chat → Studio, bound to the intended instance.** Studio gets separate Codex and Claude Code Desktop buttons. In the opposite direction an ordinary SAAM request or resumed SAAM context must find the installed release without a special prompt, pasted paths or a repository checkout. This expands the first new bug into a complete initialization workflow; implementation is pending and the mechanism below is proposed for owner selection.

**Current gap:** agent guidance selects relative checkout commands and reports Git currency; the shared checkout was also 24 commits behind release. More fundamentally, the installed launcher and stdio MCP adapter each create a runtime with a random owner; the launcher control endpoint only opens Studio. A new chat is not attached to an existing app-owned instance by opening its URL or sharing a print directory. MCP transport connection identity must not be assumed to equal conversation identity.

**Recommended common mechanism:** extend the installed application's existing local control interface to start/connect/resume a conversation's Studio association. Keep application/runtime, Studio-instance and conversation identities distinct. Agent tools become clients of the selected installed runtime; an explicit developer route selects source checkouts. Keep one Studio per bundle, one attached chat per instance, and one chat's ability to own several instances. Preserve Bundle reservations, Studio requests/events, cancellation and checked-byte export. This needs deployment/Studio/agent contract review before implementation, not another independent runtime or remote chat relay.

| Start | Intended flow |
|---|---|
| Studio first | The chosen button reserves a one-use handoff for this exact instance, prepares an isolated conversation workspace under user data and opens the chosen desktop app there. A supported startup hook or first agent connection claims that handoff for the actual client session. Display Waiting for agent until the handshake succeeds, then the client and connection state. Never infer attachment from launch success or attach whichever chat connects next globally. |
| Chat first | A once-installed user-level SAAM skill/integration recognizes ordinary requests and invokes the installed connection entry. A new conversation receives its own Studio; a resumed conversation validates/reconnects its saved association. Prior bundle context may select that bundle only if ownership permits; a new/forked chat cannot inherit another chat's authority from copied text. The runtime selects the installed release and returns version, data root and verified association. |

**Client discovery:** install SAAM's integration once for each chosen client and keep it pointing at the stable installed entry across updates; normal users should not need repeated MCP configuration or prompt recipes. Both [Codex skills](https://learn.chatgpt.com/docs/build-skills) and [Claude skills](https://code.claude.com/docs/en/skills) support implicit selection, but this remains model-mediated. Use narrow [Codex](https://learn.chatgpt.com/docs/hooks) / [Claude](https://code.claude.com/docs/en/hooks) startup/resume hooks for verified session identity and handoff/context restoration where supported; prove their behavior in the actual desktop clients. A missing/disabled integration needs first-time setup, not a promise that an unconfigured agent recognizes SAAM. A factual question about SAAM need not launch an app.

**Desktop launch limits:** [Codex](https://learn.chatgpt.com/docs/reference/commands#chats) supports a new local task with encoded prompt and absolute workspace path; the draft is unsent. [Claude](https://code.claude.com/docs/en/cli-reference) documents opening Desktop in the current directory via `claude --desktop` from v2.1.285 on macOS/x64 Windows with subscription sign-in, but takes no prompt. Prototype passing the handoff through the prepared workspace and startup context, so the user can type any normal first message without copying instructions. Opening Claude is not proof of a created/bound chat. Fully automatic chat creation/submission on a button click is not established by either documented route; client readiness/trust and a first Send may remain necessary. The previously inspected local Claude CLI was v2.1.274.

**Choices:** (A) user-level skill plus installed CLI commands using the common connection interface: smaller integration, but command/event handling and remembering association depend more on agent instructions; (B, recommended) client plugin containing that skill, an MCP adapter to the same installed application and narrow lifecycle hooks: structured operations/events and stronger resume/identity handling, at the cost of client packaging/setup. CLI remains an escape hatch to the same interface, not a second launch policy. A global per-message keyword hook can reinforce discovery but adds false triggers and client-wide coupling; do not adopt by default. Copy/paste is a diagnostic fallback, not acceptance of the requested normal flow. Private desktop APIs, UI automation and rewriting client conversation databases are not proposed.

**Binding and recovery:** bind through a server-validated, one-use handoff and conversation-scoped authority, not PID, port, working directory, a global current instance or an owner ID copied from a prompt. Keep control credentials in local protected state. Validate replay, concurrent claims, stale process incarnations, reconnect and explicit handover; a chat disconnect must not quit a user-opened Studio. Model compaction/resume restores context; a fresh chat requires its own claim. Distinguish waiting, connected, disconnected and incompatible-client states. Installed/running version mismatch must surface an orderly restart/update path without interrupting another active job. Activation/service failure never gates local work; missing SAAM follows the installation guide.

**Implementation order and acceptance:** first prove both desktop launches, workspace/session identity and same-instance handshake in a bounded prototype; establish the common connection contract; route MCP/CLI and app startup through it; package client discovery/hooks and both buttons. Exercise both directions in both clients on declared platforms, two simultaneous chats/instances, resume/fork, reconnect, expired/replayed handoffs, absent/old client, no installation, older checkout beside a newer release and update/restart with user data preserved. A normal user message must edit the intended bundle and return its events to the correct chat. No full-suite or new-test requirement; use practical trials and focused existing checks.
